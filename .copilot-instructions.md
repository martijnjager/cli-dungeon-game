# GitHub Copilot Instructions - CLI Dungeon Game

Use this document as the project-specific guidance for generating and editing code. Match existing practices unless a change request explicitly says otherwise.

## Project Snapshot

- **App type:** CLI turn-based dungeon game
- **Language/runtime:** PHP 8.1+
- **Style:** PSR-12-ish, typed properties, return types, light PHPDoc
- **Architecture:** Command pattern + small service container
- **Namespace:** `CliGame\` for `src/`
- **Tests:** PHPUnit, tests are in the global namespace

## Structure and Design

```
src/
    Command/Actions/        # CLI commands (extend Command)
    Service/                # Container, IO, battle/shop services
    Character/              # Player/monster models, weapons, attack options
    Enum/                   # Difficulty, map direction, room type, monster type
    Balancer/               # Difficulty profile and scaling
    Trait/                  # Shared behaviors (attack, health)
    Map.php, Room.php, ...  # Core domain objects
tests/                    # PHPUnit tests (no namespace)
```

### Core Patterns

- **Command pattern:** Every CLI command extends `CliGame\Command\Command` and implements `getName()`, `help()`, and `execute(array $arguments): CommandResult`.
- **Command discovery:** Commands are auto-discovered by `CommandDiscovery` from `src/Command/Actions`. Do not add manual registration.
- **Singleton container:** `Container::getInstance()` provides lazy autowiring and shared instances. Prefer container for shared services, but follow local conventions in each class.
- **Enums:** Use `CliGame\Enum\*` enums instead of magic strings or integers.
- **Traits:** Shared combat/health behaviors live in traits; reuse instead of duplicating logic.

## Coding Style and Conventions

- **No global strict types.** Existing files do not declare `strict_types=1`. Do not add it unless the file already has it.
- **Namespaces:** All `src/` classes are under `CliGame\...`. Tests generally have no namespace.
- **Type hints:** Use typed properties and method return types. Use PHPDoc for complex arrays or generics.
- **Visibility:** Default to `private` or `protected`. Keep APIs small and focused.
- **Formatting:** 4-space indent, braces on next line for classes/methods, PSR-12 style.
- **Strings and output:** Use `CommandResult` for command output; `IO::writeLine()` or `echo` only when established in that context.
- **Randomness:** Use `mt_rand()` / `mt_getrandmax()` as in existing code.
- **Error handling:** Throw `RuntimeException` for invalid configuration or unrecoverable state; bubble exceptions instead of silent failure.

## Command Implementation Guidance

- **Name:** `getName()` returns the command keyword (lowercase, e.g. `move`).
- **Arguments:** Commands receive `array $arguments` as strings.
- **Flow control:** Use `CommandResult::continue($message)` or `CommandResult::quit($message)`.
- **Help text:** Provide a short, single-sentence description.

## Testing Practices

- **Framework:** PHPUnit.
- **Naming:** `*Test.php` files under `tests/`.
- **Setup:** Tests create `Player`, `Map`, and `Container` as needed; use in-memory or anonymous subclasses to control randomness.

## Config and File IO

- **Config loader:** `ConfigFileLoader` reads JSON config and validates object shape. Use exceptions with clear messages.
- **Filesystem:** Prefer Symfony Filesystem where already used.

## When Editing or Adding Code

- Follow existing patterns within the file; do not re-architect without a specific request.
- Keep methods small and focused; favor readable control flow over cleverness.
- Maintain current command discovery and registry behavior.
- Update or add tests when behavior changes.

### Return Command Result
```php
return CommandResult::continue('Success message');
return CommandResult::quit();
return CommandResult::error('Error message');
```

### Retrieve Services
```php
$battleService = $this->container->get(BattleService::class);
$shopService = $this->container->get(ShopService::class);
```
